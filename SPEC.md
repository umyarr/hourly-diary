# Требования и реализованное поведение v0.1.0

Функциональная спецификация однопользовательского Telegram-дневника. Настройки конкретного бота и владельца задаются вне исходного кода.

## Расписание и доступ

- Ежедневно 09:00, 10:00, …, 21:00 **Europe/Moscow**, 13 вопросов о предыдущем часе; первый о 08:00–09:00, последний о 20:00–21:00. Ежедневность и границы больше не открытый вопрос.
- Отправка инициируется только в соответствующую минуту HH:00 (00–59 секунд); с 21:01 автоматических напоминаний нет. Время фактической доставки зависит от Telegram.
- Без догоняющей рассылки после паузы/простоя. `/pause` сохраняется; `/resume` продолжает со следующей границы часа. `/start` объясняет сценарий и активирует известного владельца, но не снимает уже заданную паузу. Заданный CHAT_ID позволяет начать без /start.
- Owner whitelist — только заданный положительный числовой OWNER_ID и private chat того же владельца. Пользователь не регистрируется автоматически по первому `/start`.

## Записи

- **Текст и voice принимаются круглосуточно, включая ночь и паузу**. Интерактивные подтверждения/ответы на команды разрешены вне окна; внеплановых автоматических STT push нет.
- Reply на известный вопрос сохраняет исходный период, даже через несколько дней. Reply на запись наследует её цепочку. Несколько ответов — отдельные дополнения.
- Сообщение без reply — свободная запись с датой сообщения в Moscow, без автоматического назначения последнего часа. Категорий, форм и AI-пересказа нет.
- Ранний reply до возврата send_message хранит reply_message_id; после получения ID вопроса связь и дата восстанавливаются по точному совпадению вместе с дочерними дополнениями. По времени связь не угадывается.
- Если исход отправки так и остался unknown, reply остаётся с явной unresolved-связью в JSON; оригинал не теряется. Ручного интерфейса произвольной перепривязки в v0.1 нет.
- Время сообщения, получения, правки и период разделены. Дата ответа с периодом — дата начала периода; свободной записи — дата сообщения.
- Тексты сохраняются полностью. Полученные Telegram edits дают ревизии с оригиналом. Если первый увиденный update уже edited, отмечается original_unknown, неизвестный первоначальный текст не выдумывается.

## Голос

- Сохранить metadata (message/file IDs, MIME, размер, длительность), оригинал audio/OGG, SHA256 и транскрипт отдельно.
- Groq HTTP adapter: `whisper-large-v3-turbo`, HTTPS endpoint, User-Agent, timeout 120 секунд, chunk-loop до EOF с суммарным лимитом ответа 2 MiB. Также есть OpenAI и `none`.
- Внешний STT настраивается оператором. Ключ провайдера не входит в код или экспорт. Native Telegram transcription/MTProto для ботов не используются.
- Загрузка и STT — долговечные jobs одного процесса, не блокируют текст. Network/429/5xx — до 5 попыток с backoff; 403/невалидный JSON — явная постоянная ошибка, без платного автоповтора. `/retry` — дополнительная служебная команда (не добавлена в 8 профильных команд) для повторной обработки ошибок после исправления причины.
- `/correct новый текст` reply на voice хранит исправление, не уничтожая исходник/машинный транскрипт. Обычный reply — дополнение.
- Лимит audio 20 MiB. Перед загрузкой проверяется общий бюджет DATA_DIR 500 MiB; при превышении сохраняются metadata и явный capacity_error, без молчаливого удаления. Диск/SQLite могут исчерпаться отдельно: отказ записи не подтверждается как успешный.

## Надёжность и хранение

- Один aiogram/asyncio процесс, SQLite schema v1, WAL/FULL/foreign_keys, сериализованные операции через thread worker. Локальный process lock защищает тот же DATA_DIR, но не другой хост/каталог.
- Update и offset сохраняются одной транзакцией **до следующего getUpdates**. Unauthorized payloads не сохраняются. После обработки raw inbox body очищается, update_id остаётся для дедупликации.
- Уникальность updates/messages, ревизии и версии entries, перезапуск media jobs без дублей записей. Sending prompts/ответы при аварии становятся unknown: exactly-once Telegram send не обещается и слепого повтора нет.
- Сервер — источник данных; выключенный ноутбук не влияет на сохранение ответов. Telegram хранит неполученные updates ограниченное время, долгий простой VPS не покрывается обещанием бесконечного восстановления.
- Backup: SQLite online backup + SHA256 audio objects, 14 поколений БД, проверка integrity и restore. Независимая локальная/off-host копия хранится вне Яндекс Диска. Retention не удаляет дневник/аудио; автоматического GC shared objects нет.

## Выгрузка по запросу и Obsidian

- Безусловная автоматическая синхронизация записей в Obsidian не используется. Владелец нажимает кнопку «🗂 Синхронизировать с Obsidian» или отправляет `/sync`; сервер ставит одну pending-команду. Локальная задача polling каждые 5 минут только проверяет её и запускает ровно один pull. Без команды нет snapshot/download/изменения vault. Уже доставленные файлы сохраняются. Server/off-host backup продолжают работать.
- `/export` без аргументов и кнопка «📦 Выгрузка» показывают подсказку и не отправляют архив.
- `/sync` и кнопка Obsidian отвечают `запрошена`; повтор при состоянии requested/running не создаёт дубль. После локального poll статус становится `выполнена` или `ошибка`; `/status` показывает последний статус. `/today` — ZIP за сегодня; `/export сегодня`, `/export вчера`, `/export DATE` или `/export DATE DATE` — выбранный период, включительно, до 31 дня. Даты считаются в Europe/Moscow.
- ZIP включает Markdown, JSON schema_version=1, доступные audio и manifest SHA256. Подпись сообщает период и размер архива. Более 45 MiB — явная ошибка без отправки; выбрать меньший диапазон. Архив не отправляется после записи или автоматически.
- В JSON: stable ID/version, период/null, времена, исходный/текущий текст и ревизии, voice/transcript/correction/status, parent и source reply IDs. Не включать file download URL, токены, file_id и другие лишние metadata Telegram. Ошибки/отсутствующее аудио явно меняют complete=false.
- Vault задаётся оператором; записи хранятся в `Daily/YYYY-MM-DD.md`, аудио — в `Attachments/hourly-diary/`.
- Полный snapshot по SSH/SFTP, без публичного HTTP endpoint. На Windows atomic attachments и managed-block merge с сохранением ручных секций; ID/version не дают дублей. Изменения текста/STT/даты обновляются, старый snapshot отвергается.
- Локальная квитанция ID/version/day — не подтверждение облачной синхронизации. На сервере нет destructive ACK: записи и аудио остаются и доступны заново.
- Проверка concurrent edits, резервная предимпортная версия, явная ошибка конфликтных маркеров. Микрогонка с некооперативным редактором полностью не исключена. Ручные изменения внутри управляемого блока могут заменяться серверной версией; вне блока сохраняются.

## Критерии приёмки

Локальные: 13 границ и пропуски; пауза/restart; whitelist; full text/voice/free/reply/edit/correction; durable poll/replay; ранний reply до sent_prompt с потомками; STT chunking/errors/лимиты; состав и checksums ZIP; сохранение ручных секций, stale rejection и перенос дня sync; backup integrity/restore; независимый backup pull; installed package вне cwd.

Развёртывание проверяется отдельно от функциональных требований: service health, доступ Telegram и STT, экспорт, синхронизация, резервное копирование и восстановление.

Вне версии: аналитика, создание задач, автоматическое удаление по Telegram delete, локальная тяжёлая STT, шифрование диска, автоматический GC и полноценный UI перепривязки unknown reply.
